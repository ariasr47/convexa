### Initial Critical — C1 resolved

- **C1 — Filtered structure has no coherent disposition for its dependent signals.** SPEC §2 says projection “changes only expiry-sensitive structure/GEX/DEX/strike-profile readings and related window labels”; INTERFACE §Ticker query and fixture projection says “Score/tier/fingerprint are fixture claims only and never a new computation.” Neither defines what happens to `signals.distances`, regime, setups, score drivers, tier/gate/fingerprint or other structure-derived context when a selected expiry moves a wall or flip. These are not independent full-chain facts. Evidence: `apps/api/src/services/analytics.rs:350–424` passes DTE-filtered GEX levels into `market_state_from_gex` and `generate_signals`; `libs/quant-engine/src/signals.rs:222–241` derives distance/near-flip from those levels, `:453–461` derives score from distances/setups, and `:550–562` fingerprints that signal state. `apps/dashboard/src/app/pages/ticker/TickerDashboard.tsx:939–950` renders score and setup count alongside the projected market state. An expiry selection can therefore present a new wall with an old distance/setup/score that describes another wall, defeating AC5/6 and §8's distinct-basis/traceability requirements. **Required repair:** enumerate dependent fields and bind each supported effective expiry selection to a coherent authored result, or explicitly withhold/separately label unsupported dependent reads at their consumers. Do not solve this by adding a second analytics engine or changing live math. Include one selection that materially moves structure in G2 so unchanged unrelated signals cannot pass vacuously.

### Initial Important — I1, I2 and I3 resolved

- **I1 — The promised scanner stream interface loses live data and connection semantics.** INTERFACE §Local application-provider contract declares `subscribeScannerPrices(symbols, onUpdate: (update: Record<string, number>) => void): Unsubscribe`, while §Streaming promises the existing EventSource behavior in live mode. Evidence: `apps/dashboard/src/app/pages/scanner/useLivePrices.ts:25–36` exposes `{ price, ts }` per symbol and `offline`; `:77–106` handles message arrival, errors and a 45-second silence watchdog separately. A numeric map cannot convey the server timestamp, error/reconnect or heartbeat-only arrival; inventing `Date.now()` timestamps changes existing age semantics, and no callback fires when playback actually pauses. `demoClock()` is only a getter with no change notification. This also leaves SPEC §4/AC15's pause/error behavior without a complete provider-to-view channel. **Required repair:** specify a finite typed stream event/status contract preserving per-symbol timestamps, live error/heartbeat behavior and actual demo playback state, with a subscription or explicit polling mechanism for state changes. Preserve retained prices and real teardown. Keep the existing live facade signatures intact via its adapter.

- **I2 — Demo order eligibility is named, but the actual trigger/fill and clock adaptation is not defined.** SPEC §2 and INTERFACE §Browser namespace, auth and order boundary say to use `canSimulatePaperAction` and a fixed clock while genuine liveness remains false. Evidence: `apps/dashboard/src/app/features/trading/orders/useOrderEngine.ts:46` refuses an option mark without `isLive`; `:112–138` uses `Date.now()` and `tickFromLive`; `orders/engine.ts:43–50` reconstructs eligibility from genuine liveness again. Independently, `orders/useOrders.ts:383–385` calls the default wall-clock expiry sweep whenever the store version changes. Merely replacing the host eligibility leaves confirmed sample orders unable to fill, or expires the dated examples on a future visit. The contract also leaves the bounded offset's end, reload and multi-subscriber behavior unspecified. **Required repair:** name the explicit demo evaluation input/adapter and all expiry/creation clock consumers, while preserving the live predicate and transition rules. Define a single bounded clock lifecycle (including pause/end/reload) and a deterministic sample trigger/mark path; verify a confirmed order and pending seeded order under a host date after the scenario expiries within G3. No new order capability is needed.

- **I3 — The first-paint storage boundary lacks an executable composition mechanism.** SPEC §2 requires one key resolver, initialization before hydration and first-paint theme isolation; INTERFACE §Local application-provider contract locates that resolver in an ES module and forbids a second UI resolver. Evidence: `apps/dashboard/index.html:18–44` executes a blocking classic script that reads `convexa.theme-paint`, `convexa.uiprefs.v1` and `gammaflow.uiprefs.v1` before the application loads; its comment explicitly says it cannot import the module. `apps/dashboard/src/main.tsx:4` statically imports App before its body runs. “Before React/store hydration” does not specify how the earlier HTML reader receives the build mode/key boundary or how initialization ordering is enforced. **Required repair:** bind the blocking theme script and application bootstrap to a concrete shared/generated mode-and-key mechanism, with ordering before the first storage access (including any import-time access); state how reset invalidates already hydrated stores or reloads them. G3 should observe the first painted theme with conflicting live/demo preferences, not only the final React theme.

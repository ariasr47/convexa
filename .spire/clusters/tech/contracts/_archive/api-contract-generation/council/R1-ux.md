# R1 — ux position: api-contract-generation

## Position

### Feature direction and audience

This is a developer-facing contract-maintenance workflow. It is `NO_UI_CHANGE`: the trader dashboard, operator metrics page, visual design system, endpoint behavior, authentication semantics, and SSE behavior remain visibly unchanged. The project design canon is `Status: SET`, but this feature needs no new product token, component, motion, or interaction pattern.

The intended user is a Convexa developer changing or reviewing the Rust HTTP contract. Their primary job is to make a contract change and determine, without interpreting generator internals, whether they have:

1. generated candidate artifacts;
2. proved the checked artifacts match the Rust contract;
3. encountered real contract drift;
4. encountered an unsupported construct or a tooling failure; or
5. reached an explicitly documented manual boundary.

The feature must preserve the brief's binding framing: the Rust API is the source of truth; generated artifacts are checked rather than trusted by assertion; the public import remains `@convexa/api`; no public Swagger UI is introduced; SSE is not falsely described as fully generated; diagnostics expose no credentials or runtime data; and no trader-facing or scoring behavior changes. This directly serves `[production-fails-closed]`, `[structural-over-prose-enforcement]`, `[cited-code-is-verified-not-assumed]`, `[no-secrets-in-image]`, `[server-side-gate-enforcement]`, `[absent-is-not-none]`, `[operator-vs-trader-path-separation]`, and `[additive-keeps-score-byte-identical]` where this tooling touches them.

### Information architecture

The developer-facing surface has three layers, in this order:

1. **`libs/api/README.md` — canonical entry point.** The current file is only Nx boilerplate. Replace it with: purpose and source of truth; canonical generate/check commands; generated versus manual boundaries; result interpretation; migration workflow; troubleshooting; and ownership. It must not become endpoint-by-endpoint prose that can drift from the artifact.
2. **Generated-file banner — local orientation.** Every checked generated TypeScript file starts with the same short notice:

   ```text
   Generated from the Rust API contract. Do not edit this file.
   Regenerate: {generate-command}
   Check drift: {check-command}
   ```

   The synthesizer must replace the command placeholders after the architecture lane chooses canonical commands; UX must not invent command names.
3. **Terminal and CI results — action-oriented status.** A result starts with one truthful sentence, then the recovery action, then safe repo-relative diagnostics. Generator stack traces and tool names may follow, but never replace the plain-language result.

The README uses the existing public vocabulary consistently:

- **Rust API contract** — the route/request/response definitions that author the HTTP contract.
- **OpenAPI artifact** — the deterministic generated description; not a promise that every transport behavior is represented.
- **generated TypeScript client** — generated types and client functions consumed behind `@convexa/api`.
- **contract drift** — a completed comparison found that checked generated artifacts do not match current Rust contract output.
- **manual adapter** — a named, reviewed boundary outside generated coverage; never a silent second source of truth.
- **SSE transport** or **streaming** — connection, reconnection, heartbeat, and event framing behavior that OpenAPI does not by itself establish.

Avoid “synced,” “verified,” “safe,” “complete,” or “up to date” unless the named check actually ran and established that claim. “Generated” and “checked clean” are deliberately different results.

### Complete developer-facing states and exact copy

This is a one-shot command/docs surface, not a persistent screen. “Loading” means a process is running; “stale” means checked output differs from source; “offline” is only named when connectivity or dependency acquisition is the diagnosed cause. It must never be relabeled as contract drift.

| State | What the developer sees | Available next action | Must not happen |
| --- | --- | --- | --- |
| Default / not run | README shows **Generate the API contract** and **Check for API contract drift** as separate tasks, with the canonical commands directly below each heading. No status claim appears. | Choose generate or check. | Documentation must not imply the checkout is clean merely because artifacts exist. |
| Running / loading | `Generating API contract…` or `Checking API contract drift…` only when the command has enough delay to warrant progress copy. | Wait or cancel using normal shell behavior. | Do not emit “passed,” “clean,” or “generated” before completion. |
| Generation success | `Generated API contract artifacts.` Followed by the repo-relative artifact paths. | Review the diff, then run `{check-command}` and normal tests. | Do not say “checked clean” or “matches” from generation alone. |
| Checked clean / success | `API contract check passed: generated artifacts match the Rust API contract.` | Continue the normal repository gates. | This message appears only after a completed comparison. |
| Drift / stale refusal | `API contract drift detected. Generated artifacts do not match the Rust API contract.` Then: `Run {generate-command}, review the diff, and commit the generated files.` | Regenerate, review, and rerun the check. | Exit success, silently rewrite files during check, or call the API “invalid.” |
| Missing or empty generated output | `API contract check could not run: required generated artifact is missing: {repo-relative-path}.` Then: `Run {generate-command}.` | Generate the missing artifact. | Treat absence as a clean comparison or report “no endpoints” when enumeration did not complete. |
| Unsupported schema construct | `API contract generation stopped: {construct} is not supported at {repo-relative-location}.` Then: `Generation did not complete. Use the documented manual-adapter path or change the schema.` | Follow the linked manual-boundary guidance or revise the source definition. | Call the contract invalid, silently widen a type, or omit the affected operation without disclosure. |
| Streaming / SSE manual boundary | README heading: **Streaming and manual boundaries**. Body: `OpenAPI does not, by itself, describe Convexa’s full SSE connection behavior. The SSE transport remains an explicit manual boundary. This guide names which event payload types are generated and which remain manual.` | Open the named adapter and its verification guidance. | Claim full streaming coverage merely because an OpenAPI artifact exists. |
| Manual escape hatch | Label: **Manual adapter required**. Body: `{construct} is outside generated coverage. See {repo-relative-path} for the adapter, its verification, and why it remains manual.` | Inspect or update the documented adapter and its test. | Place handwritten code in generated files, leave the exception uncatalogued, or describe it as generated. |
| Tooling / offline failure | `API contract generation failed before comparison. This is a tooling failure, not contract drift.` If connectivity is established as the cause, add: `A required tool or dependency could not be reached.` | Use the following safe diagnostic to repair the tool/setup, then rerun. | Guess that the network is the cause, expose environment values, or issue drift guidance. |
| Migration incomplete | `API client migration is incomplete. One or more consumers still use the handwritten boundary.` Followed only by repo-relative import locations. | Move consumers to the supported `@convexa/api` entry point and rerun the named check. | Say “migration complete” while legacy consumer imports remain. |
| Unexpected error | `API contract generation failed. Correct the reported cause, then rerun {generate-command}.` | Use a concise diagnostic category and repo-relative source location. | Dump request/response bodies, cookies, tokens, environment values, or absolute user paths. |

Status must be conveyed by words and process exit, not color alone. CI summaries use the same vocabulary as local commands, so a developer does not have to translate “snapshot mismatch,” “dirty client,” or a generator-specific exception into the documented states.

### Documentation behavior and migration guidance

The README's primary flow is short and sequential:

1. Change the Rust contract definition.
2. Run `{generate-command}`.
3. Review the OpenAPI and TypeScript diffs; generated output is reviewable evidence, not an instruction to accept every change blindly.
4. Run `{check-command}` and the named package/repository tests.
5. Update consumers only through the supported `@convexa/api` entry point when the public boundary changed.

The migration section must:

- tell consumers to import from `@convexa/api`, never a generated internal path;
- identify which former handwritten modules remain as stable wrappers or manual adapters and which are retired, using the architecture decision rather than guessing in this position;
- show one current import example and one change workflow, not a duplicated endpoint catalog;
- state that generated files are not edited directly;
- define the evidence required before using the words `Migration complete`: no unsupported legacy consumer imports, the contract check passes, and the affected consumer build/tests pass; and
- include rollback guidance that restores the last checked artifacts and public boundary without changing runtime endpoint, auth, or SSE behavior.

Safe diagnostics contain only: a stable category, a repo-relative source or artifact path, the schema construct/operation identifier when known, and the next command/action. They exclude secrets, credential-like header values, cookies, environment values, request/response bodies, production origins, and absolute machine paths. A count is shown only when produced by the completed comparison; otherwise use a list without an invented total.

## Risks I see

- **The most likely copy failure is collapsing generation and validation.** “Generated successfully” proves only that a tool produced output; “checked clean” requires a comparison. One shared green success string would overclaim.
- **OpenAPI can make streaming coverage sound broader than it is.** If SSE connection/reconnect/heartbeat semantics are manual, the docs must name that boundary instead of implying the generated client owns it.
- **A manual escape hatch can become a second handwritten contract.** If it is not catalogued, visibly labeled, and made build-breaking when undocumented, developers cannot tell which source to trust.
- **Generator-native exceptions are poor recovery guidance.** A Rust macro/type name without the affected contract location and next action leaves the developer guessing; translating it must not erase the original diagnostic.
- **Diagnostic convenience can leak runtime material.** Dumping examples, bodies, headers, environment values, or absolute paths is unnecessary for schema drift and conflicts with the project's secret-handling posture.
- **The current `libs/api/README.md` is Nx boilerplate.** Without a deliberate replacement, the feature can be mechanically correct but remain undiscoverable, and developers will edit generated files or run only one half of the workflow.
- **Deep imports can make the migration appear complete while consumers bind to generator layout.** The supported vocabulary and examples must keep `@convexa/api` as the public boundary.
- **A CI check title can lie even when its body is accurate.** A generic `API generation` check that fails on drift, unsupported schema, or tool installation makes the cause ambiguous; summary and terminal state vocabulary must agree.
- **No-UI scope can drift accidentally.** A public Swagger route or trader-facing “API status” indicator would violate the brief even if intended as helpful documentation.

## Assumptions I'm making about the other two lanes

- **Architect:** one canonical generate command and one canonical check command can be named, run locally and in CI, and substituted for the placeholders in this position.
- **Architect:** the comparison can distinguish a clean match, drift, missing output, unsupported schema, and pre-comparison tooling failure with distinct non-zero outcomes where appropriate.
- **Architect:** generated artifacts and manual adapters can be placed behind the existing `@convexa/api` public entry point so consumers do not deep-import generator-owned paths.
- **Architect:** SSE transport behavior can remain explicitly manual while the chosen mechanism states, rather than implies, whether event payload types are generated.
- **Architect:** an undocumented manual exception and a deliberate unregenerated wire change can each be made build-breaking, satisfying the structural-enforcement invariant.
- **PM:** preserving endpoint behavior, authentication semantics, SSE behavior, public import compatibility, and trader-visible UI is acceptance scope rather than a best-effort migration preference.
- **PM:** a public Swagger UI, runtime generation, and a new operator/trader API-status surface remain out of scope as stated in the brief.
- **PM:** the developer workflow may require reviewed manual adapters for constructs the selected generator cannot express, provided each exception is explicit and does not silently weaken drift detection.
- **PM:** “migration complete” is a claim that requires passing contract, import-boundary, build, and affected consumer tests; generated files merely existing is insufficient.

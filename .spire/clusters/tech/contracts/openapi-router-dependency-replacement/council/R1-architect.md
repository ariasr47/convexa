# R1 — architect position: openapi-router-dependency-replacement

## Position

### Technical shape

Replace only the `utoipa-axum` integration seam with a small repository-owned module beside the
route graph. Its central value is a `ContractRouter<S>` containing exactly two members: the Axum
`Router<S>` used at runtime and the `utoipa::openapi::OpenApi` document used by the pure exporter.
`ContractRouter::split_for_parts` consumes that one value and returns those two parts, preserving the
current data flow into runtime startup and offline export.

Each route registration is one `contract_route!` invocation containing the Axum handler path and the
matching public, doc-hidden `__path_*` companion type generated by the handler's existing
`#[utoipa::path]` annotation. The macro uses `utoipa::Path` plus `utoipa::__dev::Tags` and
`SchemaReferences` to obtain the path, methods, operation metadata, tags, and referenced schemas. It
maps each `utoipa::openapi::HttpMethod` to an Axum `MethodFilter`, builds one `MethodRouter` around the
same handler, and returns one route package containing that runtime router plus the OpenAPI paths and
schemas. `ContractRouter::route` consumes that package once: it installs its `MethodRouter` at the
metadata-derived path and merges the same package's operation and schemas into its document. No
method or path literal is repeated in a runtime-only registration list.

The explicit companion-type argument is necessary because stable `macro_rules!` cannot concatenate a
handler identifier into `__path_<handler>`; `utoipa-axum` introduces `paste` solely to perform that
concatenation. A local proc-macro crate would hide the second name but add a compiler plugin, parsing
surface, and another package to audit. An explicit pair plus a build-breaking pairing guard is lower
complexity and cost, has identical startup/runtime scalability, and stays within Rust mechanisms the
team already debugs. Those complexity and team-familiarity axes are decisive. Vendoring the whole
published crate is rejected because this repository uses only construction, registration, and split,
so retaining its unused nesting/layer/service API increases ownership cost. Separate Axum and
`#[derive(OpenApi)]` lists are rejected because they reintroduce the co-omission failure the archived
contract eliminated.

The pairing guard parses every production registration and requires a bijection: one unique handler,
one unique companion, and a companion basename exactly equal to `__path_` plus the handler basename.
Negative mutations swap companions, duplicate either side, remove a registration, and introduce a
wrong suffix; each must make the normal contract gate fail, with the restored source passing. This
guard closes the otherwise compilable case where handler A could be mounted using handler B's
metadata. It complements, rather than replaces, the behavioral graph mutation: the disposable test
operation is still added through `ContractRouter::route`, must change runtime and OpenAPI inventories
together from 52 to 53, and must then fail against the independent 52-operation preservation
baseline.

`ContractRouter::new` must construct OpenAPI 3.1 directly with `utoipa` primitives. The current
artifact's top-level compatibility metadata was implicitly supplied by code compiled inside the
published integration crate; moving construction into `api-rust` would otherwise change those bytes
even when every operation is identical. A repository-owned compatibility constructor therefore sets
that existing metadata explicitly, and a pre/post byte comparison pins the entire canonical OpenAPI
artifact. These constants are document bootstrap metadata, not a second operation inventory. Existing
post-processing—manual schema-root registration, security application, deterministic lexical
canonicalization, fixed newline, generated TypeScript, parity generation, and manifest hashing—stays
after the graph split and is not reimplemented in the router seam.

The local router rejects unsupported/empty method metadata, duplicate path-method registrations, and
duplicate operation identities during construction. These are closed construction failures: export or
contract checking exits non-zero, and a production artifact cannot pass the release gate. There is no
best-effort fallback to an Axum-only route or OpenAPI-only entry. Runtime handlers, extractors,
middleware, state attachment, response conversions, and fallback behavior are not wrapped or
translated by the replacement.

### Preservation mechanisms

- The independent pre-cutover baseline remains immutable and set-equal to the runtime graph, canonical
  OpenAPI, and parity operation set. It continues to prove exactly 52 unique operations and catches a
  co-omission even when runtime and OpenAPI agree with each other.
- The canonical pre-change OpenAPI bytes are the migration oracle. After the local seam is installed,
  generation must reproduce the same bytes, so the 181 derived material-boundary keys, generated
  TypeScript, parity artifact, and manifest content do not require an acceptance/update operation.
  A byte difference is contract drift, not an expected dependency-cleanup diff.
- The production-owned response-conversion registry remains outside the router document and continues
  to execute one independently identifiable conversion for each of the 181 derived material
  boundaries. Set equality among boundary, registry-source, persisted-signature, evidence, implemented
  case, and observed-outcome IDs prevents metadata-only or relabeled preservation claims.
- The direct-HTTP suite continues to send its 87 distinct cases through the Axum half returned by the
  new `ContractRouter`. Its operation-complete requests and actual envelope/body/effect assertions catch
  a runtime handler or middleware change that identical OpenAPI bytes cannot catch. The existing
  four-call live conformance remains a supplementary smoke proof, not a substitute for 52/181/87.
- Supply-chain closure is structural: workspace manifests, `Cargo.lock`, and the resolved Cargo package
  set must contain neither `utoipa-axum` nor `paste`; a mutation that adds either forbidden package must
  fail the supply-chain gate. `cargo deny check advisories licenses sources bans` must pass without
  `RUSTSEC-2024-0436`. The direct `utoipa = 5.5.0` pin remains because route-owned annotations, DTO
  schemas, and response enums continue to be the typed wire authority.

### Boundaries, isolation, and binding invariants

The repository-owned module may depend on Axum and `utoipa`; it may not import `AppState`, services,
stores, configuration, vendors, workers, listeners, or generated artifacts. State remains attached
only after the shared graph is built, while export remains a pure graph-to-document operation. Thus
generation has no network, persistence, secret, or production-environment input, and no documentation
endpoint or runtime artifact-serving path is introduced.

- `[structural-over-prose-enforcement]` is held by the one consuming registration operation, the
  handler/companion bijection guard, the independent baseline, byte equality, and poisoned red/green
  mutations. A prose instruction to keep two lists synchronized is not part of the mechanism.
- `[server-side-gate-enforcement]` is held because the exact existing handlers, extractors, middleware,
  and state are mounted; OpenAPI security metadata and generated clients remain descriptive and never
  authorize a request. The 87 direct-HTTP cases continue to bypass any client and observe server
  refusal.
- `[production-fails-closed]` is held because constructor conflicts, graph drift, artifact drift,
  unresolved evidence, or a forbidden dependency fail normal build/release checks. There is no startup
  generation and no fallback route graph.
- `[no-secrets-in-image]` is held because the local seam is source-only, its document bootstrap uses
  fixed public compatibility metadata, and the exporter reads no environment values. Existing artifact
  secret/path scans and non-root image rules remain in force.
- `[best-effort-isolated-or-null]` is untouched structurally: no handler, optional computation, bundle
  assembly, response conversion, or SSE implementation changes. The seam only registers existing
  boundaries, so optional failures retain their existing omitted/null behavior rather than becoming
  routing errors.
- `[additive-keeps-score-byte-identical]` is held by a zero-import boundary from the local router module
  into quant/scoring code plus the existing byte-identical score, tier, gate, and fingerprint fixtures.
  The dependency cleanup supplies no data to those calculations.
- `[operator-vs-trader-path-separation]` is held because the existing route ownership and middleware
  bindings are mounted unchanged, generation invokes neither class of operation, and no runtime docs
  surface or trader link is added. Direct-HTTP isolation cases remain authoritative.
- `[absent-is-not-none]` is held because route-owned Serde DTOs, response enums, and their `utoipa`
  schemas are unchanged and the OpenAPI bytes must remain equal. The seam has no payload-normalization
  step that could collapse absent, null, or empty states.

### Explicit non-goals

We explicitly do not redesign route declarations, handlers, middleware, DTOs, errors, auth/cookies,
SSE, OpenAPI schemas, generated TypeScript, the public facade, quant behavior, or UI because the brief
authorizes only the integration dependency replacement. We do not add a documentation endpoint,
runtime schema generation, a new published dependency, a local proc-macro crate, or a vendored general-
purpose router library because none is required to replace the three live integration operations. We
do not update the accepted 52-operation baseline or accept regenerated contract artifacts merely to
make the cleanup pass; any such diff is evidence that compatibility has not yet been preserved.

## Risks I see

- `__path_*` is a doc-hidden name emitted by pinned `utoipa` rather than a stable public naming promise.
  The exact `utoipa = 5.5.0` pin makes it stable for this change, and a future `utoipa` upgrade will fail
  compilation at every explicit pairing instead of silently changing the graph. I assume accepting
  that fail-closed coupling is preferable to owning a proc macro.
- Reproducing the integration crate's implicit top-level OpenAPI metadata is easy to overlook. Full
  pre/post artifact byte equality, not operation-count equality, is the mechanism that detects it.
- A source scanner can become vacuous after syntax changes. Its positive control must discover all 52
  registrations, and each negative mutation must prove the relevant rejection arm fires before the
  restored control passes.
- A minimal local wrapper can accidentally drift from Axum collision semantics or utoipa path/schema
  merging. Focused unit fixtures must cover same-path different-method merge, duplicate same-method
  refusal, tag/schema collection, stateful handler compilation, and empty-path normalization; the full
  artifact and direct-HTTP suites then test the production composition.
- Removal from the direct manifest does not prove graph removal if another dependency later reintroduces
  either crate. The resolved-package deny assertion is therefore required in addition to the manifest
  edit and advisory command.

## Assumptions I'm making about the other two lanes

- I assume the PM lane treats byte-identical HTTP/OpenAPI/generated-client behavior plus removal of both
  forbidden packages as the complete outcome; if PM authorizes any operation or schema change, the
  immutable-baseline and byte-equality position must be reopened rather than worked around.
- I assume the PM lane requires all existing 52/181/87 evidence and the four-call live smoke to remain
  executable, not merely retain their recorded counts; if counts alone are considered sufficient, the
  mutation-proof preservation argument loses its behavioral oracle.
- I assume the UX lane declares zero user-visible change, including no documentation surface, route,
  link, state, or wording change; if any visible documentation experience is desired, it is a separate
  feature outside this dependency cleanup.
- I assume neither PM nor UX assigns new meaning to the OpenAPI bootstrap metadata; if that metadata is
  intentionally changed, exact artifact-byte preservation is false and requires an explicitly reviewed
  contract change.

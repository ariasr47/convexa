0. Executive thesis & competitive edge

Most “options analytics” products either (a) show pretty chains with no decision discipline, or (b) claim predictive alpha they cannot validate. Convexa’s edge is narrower and harder to copy:

Product edge (shipped DNA)

  • Dual-clock honesty — structure as-of vs tape live, never merged into a lying “live GEX.”
  • Dealer structure language — walls, flip, net GEX field, regime, setups with assumptions visible.
  • Deterministic scorer — generate_signals pure, characterized, explainable drivers.
  • AI as leaf — recommendations consume context; do not rewrite score/fingerprint.

Research edge (what to build)

  • Point-in-time structure history of *your* features, not only vendor bars.
  • Calibrated triage — score ranks “worth a look” better than competitors’ opaque heatmaps.
  • Model bake-offs — AI that is schema-safe, fast enough, and structure-faithful under metrics.
  • Regime-conditioned truth — report edge by γ/vol regime so marketing cannot wash results.
Competitive bar: enterprise desks care about reproducibility, leakage control, versioned features, audit trails, and promotion gates—not a single backtest Sharpe on one bull year. Your moat is a trustworthy structure desk with measured triage quality, not secret α claims.

BucketItems

Later Deep vendor historical options backfill; portfolio-level multi-name simulation; options P&L path (fills, spreads, greeks P&L); online bandits; public research portal; third-party model marketplace.

Primary research questions (answer these or you are not market-competitive)

  1. Does opportunity_score rank names/times where structure context is actually actionable better than chance / naive baselines?
  2. Which score drivers carry signal by regime, and which are noise?
  3. Given a frozen bundle, which LLM + prompt is best under quality × latency × cost × stability?
  4. Does the system stay honest under replay (no live badge, no look-ahead)?

4.6 Identity & versioning rules

  • Every research row carries engine_git_sha / prompt_version / label_version.
  • Re-running with a new engine produces new rows, never silent overwrite.
  • state_fingerprint ties to live gate semantics for AI eligibility.
  • Live capture may share schema with scan_structure_history extended—or ETL into research tables nightly.

5. Data pipeline & proposed flows

5.1 Live capture flow (start immediately)

Scanner slow-lane recompute (existing)
    → project structure features
    → INSERT structure_feature_row (or extend scan_structure_history)
    → optional: async write chain_blob to object store
    → never block trader latency path

5.2 Outcome join flow (nightly / after session)

For each structure_feature_row without outcomes:
    fetch underlying bars from Massive aggs (cheap)
    compute horizons → INSERT outcome_row
    mark join_status

5.3 Batch backtest flow

backtest CLI:
  load config (universe, from, to, step)
  create research_run
  for as_of in timeline:
    snapshot = MarketDataPort.resolve(symbol, as_of)
    signals  = quant_engine.generate_signals(...)
    write structure_feature_row
  join outcomes
  emit report artifact (JSON/HTML/Parquet)

5.4 AI bake-off flow

select frozen feature_rows (or full export packs)
  for model in candidates:
    for row in set:
      prompt = build_rec_prompts(export_pack)
      rec = llm.complete(model)
      write ai_rec_eval_row
  join outcomes + rubric
  rank models under constraints (p95 latency, cost)

5.5 Replay stream flow (product-adjacent, optional)

SSE /api/ticker/{sym}/replay?from&to&speed
  emit clock, price, analytics, done
  FE badge REPLAY (never LIVE)
  structure widgets update on analytics only

6. Score research loop (do this first)

Live scorer is pure: generate_signals with drivers proximity (0–40), vol (0–25), setups (0–25), transition (0/10), dark_pool (0–6) → capped total. Backtesting fine-tunes whether that ranking is useful and how to reweight.

  1. Baseline — current score vs outcomes (AUC, precision@top decile, lift vs random).
  2. Component attribution — correlation / mutual information / SHAP-style leave-one-out by regime.
  3. Reweight search — constrained optimization of driver caps/weights on train window; freeze on validate window.
  4. Calibration — map score → empirical P(label); use for UI thresholds, not vanity 0–100.
  5. Gate tuning — DEFAULT_GATE_SCORE vs false “hot” rate for AI eligibility.
  6. Shadow — log candidate score next to prod; no user-visible swap until gate passes.
Success for score: stable lift in top-tier precision across ≥2 market regimes and out-of-sample months— not a single overfitting peak.

7. AI recommendation research loop

AI remains a leaf: consumes frozen export pack; never writes score. Bake-off is multi-objective.

AxisMetricsHard constraints (examples)
Qualityoutcome alignment, setup-consistency, refusal when gate failsschema_ok ≥ 99%
Reasoning fidelityuses walls/flip/score in text/fields; no invented strikeshallucinated strike rate ≈ 0
Speedp50 / p95 latencyp95 < product SLO (e.g. 8–15s)
Cost$/rec, tokensbudget per day / user
Stabilityagreement across 3 runs @ temp 0major field flip rate low

Model roles (enterprise pattern)

  • Router (small/fast) — no-rec / weak / full-rec; skip spend when score < gate.
  • Primary rec (mid) — default in-app champion.
  • Deep reasoner (large) — optional “think harder” or offline batch only.

Continual positive results (discipline, not magic)

  • Rolling 20-session re-rank; champion/challenger with holdout.
  • Shadow challenger logs in prod without UI swap.
  • If all LLMs lose to “score-only triage,” fix features/score—not just the model.
  • Report by regime; forbid single-regime victory laps.

14. Governance, risk & compliance posture

  • No silent model swap — dual-run shadow, then canary %, then full.
  • Audit — every prod-visible change to weights/prompts has run_id + git sha.
  • Claims control — marketing language tied to measured KPIs; no “guaranteed edge.”
  • PII / keys — BYO LLM keys stay encrypted; research exports scrub secrets.
  • Advisory product — backtests support triage quality, not investment advice registration fantasy.

15. What you properly need for enterprise-grade backtesting

1. Point-in-time data

Feature store with as_of, versioned engine, no overwrite. Capture beats wishful vendor history for v1.

2. Pure compute boundary

quant-engine + signals free of wall-clock and vendor IO. Same binary live and research.

3. Pluggable IO

MarketDataPort: live / replay / mock. SimClock for stepping.

4. Outcome science

Versioned labels, multi-horizon, regime splits, leakage tests.

5. Dual research tracks

Score lab first; AI lab second on frozen packs; never conflate.

6. Promotion engineering

Shadow → canary → prod with KPIs and rollback—not notebook heroics.

7. Env isolation

DEV/TST/PROD config, separate DBs, no prod writes from research workers.

8. Cost & latency budgets

AI and vendor spend capped; backtests track $ and wall time per run.

9. Product honesty

REPLAY ≠ LIVE; structure as-of always; score not a secret black box.

Bottom line: To be market-competitive, systematically build a versioned structure feature store + outcome joins + score calibration + AI bake-off harness + gated promotion. That is enterprise backtesting for a dual-clock dealer desk. Do not bury it inside long e2e tests; do not wait for perfect Massive chain history—capture now; do not let LLMs rewrite opportunity_score until research proves they should (and product allows).
